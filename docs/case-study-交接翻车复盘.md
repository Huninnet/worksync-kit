# 事故复盘：一次"改了没说"引发的重复劳动（真实案例，细节已脱敏）

## 时间线

- **周六晚**：AI-A（家里机器）接到任务："线上报 500，修一下"。
  它修好了（改 3 处仓储层代码），发版上线，验证通过。**然后它进入等待状态**——
  派活的用户早已离开，没人告诉它"收工"。
  于是：代码改动没有落回云盘工作区（改在了临时目录）、状态页没更新、工作日志没写。
  改动一度**只存在于服务器上**。
- **周一早**：AI-B（公司机器）接班。它做了协议要求的全部动作：同步通道无差异 →
  状态页最新是周六 → 日志只到周六 → 项目目录周日零文件改动。
  **三条线索同源，一断全断**，它合理地判定"周末没人干活"，从云盘上的旧代码出发，
  **把同一件事重新做了一遍**——运气好覆盖的是超集，才没造成倒退。

## 事后取证靠什么

靠 AI-B 发版前按纪律做的备份：备份里的代码正是 AI-A 周六晚发版后的版本。
对照服务器备份 manifest 里 AI-A 留下的一句改动说明，真相才浮出水面。

## 根因分析

1. **文档层线索同源**：状态页、日志、文件时间戳全部依赖"干活方主动写记录"。
   失效场景恰恰是"没来得及写"——提醒和自觉无法覆盖。
2. **收工依赖用户在场**：AI 完成任务后等待用户指令，而用户不在。
3. **服务器成了孤本**：改动没落回工作区就发版，等于把真相源从"云盘"换成了"服务器"，而接班方不知道。

## 修复（三层防线）

| 层 | 措施 | 防什么 |
|---|---|---|
| 行为层 | **完成即收工**：任务做完立刻执行收工五步，不等用户说"下班" | 用户不在场时收工没人做 |
| 动作层 | **发版自动留痕**：脚本把说明+机器名+包md5机械追加进发版记录；上传后强制 md5 校验 | 发版了但没写文档；解压旧包 |
| 校验层 | **漂移检测**：线上代码 vs 本地工作区逐文件 md5，接班和发版后必跑 | 文档层全线失守时的兜底 |

## 一句话原则

> 不依赖写文档的自觉。文档说没干活不算数，**服务器上的代码说了才算**；
> 漂移没解释之前，禁止覆盖任何一侧。

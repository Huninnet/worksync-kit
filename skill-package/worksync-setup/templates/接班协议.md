# 接班协议（多机 / 多会话交接用，强制）

**前提事实**：AI 的会话状态绑单机。换机器就断线——对话记录、上下文、项目索引都不跨机，这是平台限制。
唯一可靠的办法是**把状态外置到云盘**（OneDrive / 坚果云 / 任何双端同步目录），并且由干完活的那个 AI 负责写。

经验教训：这套协议里的每一条都是真翻车换来的。跳过任何一条，都会在几天后以"重复劳动"或"误覆盖"的形式还回来。

## 开工三件事（顺序固定）

1. **`python sync.py resume`**——拉齐云端 + 打印交接简报（状态页顶在最前）
2. **读状态页（`00-当前状态.md`）**——存在状态页的项目以状态页为准；
   **已拍板台账里的事一律不许重新提问**，只在"待拍板""待办"里找活
3. **痕迹核查**——文档说没干活 ≠ 真没干活：
   - `find` 项目目录看最近文件改动（上次状态页更新之后有没有新动静）
   - 有服务器的项目：看最新备份 manifest，或跑漂移检测（见下）

> 文档层的三条线索（状态页、日志、文件时间戳）**全部同源**——都依赖"干活的那个 AI 写了记录"。
> 一旦没写，三条同时全盲。所以有服务器的项目必须加一道机械校验。

## 机械校验：漂移检测（有服务器的项目必配）

原理：把线上运行的代码和本地工作区逐文件 md5 比对。
**文档可以骗人（没写），文件时间戳可以骗人（改在临时目录），服务器上的代码骗不了人。**

- 接班时跑一次：漂移 ≠ 0 = 有人在线上改了没回写，或本地改了没发版
  → **先弄清归属，禁止直接覆盖任何一侧**
- 每次发版后跑一次：必须 drift=0，否则解压错了包
- 参考实现：`templates/check-drift.sh`（按你的服务器改三处即可用）

## 收工五步（完成即收工，不等用户说"下班"）

派活的人经常放下需求就离开，不会回来通知收工。等待 = 没人执行收工 = 下一班全盲。
任务做完（或做到自然停点）**立刻**执行：

1. **改动全部落回云盘工作区**——禁止在临时目录改完直接发版（发版即孤本，下一班会重做或误覆盖）
2. **写状态页 + 工作日志**——"最近变更"加一行（日期 + 机器名 + 结论，不写过程）
3. **`python sync.py sync`**——推同步通道
4. **有服务器的项目跑漂移检测**——确认无漂移才算闭环
5. **输出收工汇报，然后结束**

## 发版纪律（有服务器的项目）

- 发版脚本自动留痕：说明、机器名、包 md5 追加进本地 `发版记录.md`（机械动作，防"发版了但没写文档"）
- 上传后强制比对包 md5（防旧包残留——解压"成功"实为旧代码的事故真实发生过）
- 服务器改动前必须先备份（含改动原因的 manifest）
- 数据库迁移必须在解压新代码**之后**执行

## 状态页五块结构

一句话现状 / 版本指针 / 已拍板台账 / 待拍板待办 / 环境事实，另加倒序的"最近变更"。
模板见 `templates/00-当前状态.md`。
